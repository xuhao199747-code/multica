# Multica 定制自托管的一键官方更新

## 目标与边界

部署管理员从 Web 侧边栏点击一次，即可把**官方最新稳定发布版**合入已推送的 Multica 定制代码，经过检查后更新当前 Docker Compose 网站。保留定制功能；更新失败不得伪装为成功，也不得无限创建修复任务。

本功能只更新这套 Multica 自托管服务，不是任意项目的发布系统，也不更新 Desktop、Mobile 或智能体 CLI。未配置本机更新执行器的安装仍可查看官方发布信息，但不能执行一键更新。

## 当前事实与首次启用

- 现有 `UpdateStatus` 只比较官方 `main` 与硬编码的定制分支父提交；点击文字仅重新检查，外链打开 GitHub。它既没有检查正式发布版，也不知道网站部署了哪个提交。
- 当前自托管服务使用 `docker-compose.selfhost.yml` 加 `docker-compose.selfhost.build.yml`，运行 `multica-backend:dev` 和 `multica-web:dev`。镜像没有可信的源码提交标记，不能从 GitHub 分支推断当前网站版本。
- 首次启用需由部署管理员在主机上配置：现有定制远端分支、本机仓库与 Compose 配置位置、生产数据库名、允许触发更新的账号 ID、Multica 项目 ID、外部健康检查 URL。该项目须开启项目工作流并绑定 Mika、开发、审核智能体；缺项时入口显示“需要配置”，不启动更新。此设置不影响其他项目是否启用工作流。
- 不猜测现有 `dev` 镜像的来源。启用前进行一次**明确确认的基线部署**：从选定的已推送定制提交构建带提交 SHA 的镜像，备份、部署并通过健康检查后，记录源码 SHA、镜像 digest，以及经 Git 祖先关系验证已包含的官方稳定版标签。无法验证标签时不建立基线。基线未建立时，不显示“立即更新”。这次部署须单独确认，不由发现更新自动触发。

## 入口与状态

原侧边栏更新入口保留。检测来源改为官方稳定 Release 的固定标签与提交 SHA；预发布版和官方 `main` 普通提交不触发“有官方更新”。提示依据是**已成功部署**的官方版本，不是远端分支 HEAD；检查失败显示“无法检查”，不猜测有更新。

部署管理员点击后打开确认框，展示目标版本、当前已部署定制提交、将使用的远端分支、可能短暂中断以及数据库备份。确认后显示持久化的步骤与结果；同一安装同时只允许一个更新。非部署管理员不能触发，后端也独立校验权限。完成、失败及需要处理状态都可点开执行记录和 Mika 对话；刷新页面不丢状态。

## 执行链

1. Web 后端只创建带幂等键的更新记录，不获得主机 Docker 控制权。独立运行在部署主机上的更新执行器领取记录，并在本机持久化阶段与日志。执行器只接受预先配置的仓库、分支、Compose 项目和目标稳定版，不能把网页请求当作任意 shell 命令。
2. 执行器固定官方 Release 标签和远端定制分支 SHA，在隔离工作树合并；不读取或修改用户当前工作树中的未推送文件。合并候选必须经过项目约定的 Web/Go 检查、镜像构建，并交给项目绑定的审核智能体检查官方改动对定制功能的影响；审核智能体只出结论和证据，不改代码或派任务。管理员点击确认即授权这次固定范围的更新执行，并在其项目 Mika 聊天中冻结目标版本、代码范围、验收条件与风险快照，供开发和审核任务共用；不额外要求 PRD 智能体产出文档。审核通过后才能推送定制分支，且只能非强制快进；若分支中途变化，停止本次更新，绝不覆盖别人的提交。
3. 测试通过且候选已推送后，核对生产 Compose 配置及数据库身份，完成可验证的 PostgreSQL 备份，再部署带唯一提交标签的 backend/frontend 镜像。不得 `down -v`、删除卷或重建 PostgreSQL/Tailscale；不得把开发 `.env` 当作生产数据库配置。
4. 只有后端 `/readyz`、从实际 Compose 端口取得的本地网站 URL、已配置的 Tailscale URL 都通过，才记录目标 Release、定制提交与镜像 digest 为“已部署”，显示成功。`/health` 不能替代 `/readyz`。

## Mika 自动修复与汇报

合并冲突、部署前测试或构建失败，或审核结果为 `needs_changes` 时，本次更新最多自动创建**一条** Multica 项目的真实修复任务。Mika 将目标 Release、候选提交、失败步骤及日志交给项目绑定的开发智能体；开发提交代码和测试证据，审核智能体复审。项目工作流原有的最多两轮返工上限继续生效。审核通过后，执行器仅重试本次更新一次；再次失败或审核未通过即停止，不再创建修复任务。

Docker、凭据、网络、备份和部署后健康故障不交给代码智能体盲修。同一更新进入修复阶段时最多投递一次 Mika 协调运行；进入最终成功或失败状态时最多投递一次 Mika 汇报运行，两类事件分别按更新编号幂等。目标是触发更新的管理员在 Multica 项目中的 Mika 聊天；Mika 基于真实记录汇报版本、测试、部署和待处理事项，系统不能伪造 Mika 的回复。后端不可用时，执行器保留本机记录，服务恢复后幂等补投；持续宕机时站内 Mika 无法实时通知，管理员须查看主机更新日志。

## 失败与恢复

- 部署前任何失败都不触碰当前网站。失败状态保留证据与重试入口，但无自动循环重试。
- 备份失败不部署。部署后检查失败不得显示成功；保留原镜像、备份及日志，明确列出人工恢复步骤。数据库迁移可能前向不可逆，因此不承诺自动回滚数据库，也不盲目切回旧镜像。
- 远端分支已推送而部署失败时，记录“源码已更新、网站未更新”；下一次由管理员明确触发恢复/重试，版本提示仍按实际部署提交计算。

## 验证

- 权限与并发：非部署管理员、未配置实例、重复点击、旧请求重放均不能启动额外更新。
- 版本与代码：仅稳定 Release 触发；候选来自已推送定制分支；工作树脏文件不参与；远端分支变化或冲突不会覆盖现有代码。
- 任务链：所有候选都有真实审核运行；自动修复有真实任务、运行、提交和复审证据；同一更新最多一条自动修复任务、一次更新重试；Mika 同类事件有更新编号且不重复。
- 部署：备份失败阻断；数据库及卷不被删除；`/readyz` 与两个配置化网站 URL 都通过才成功；后端重启、页面刷新或失败后仍可查状态。测试用假 Git/Docker/智能体执行器覆盖失败矩阵；真实生产升级不属于自动测试。
